# Phase 5 Dynamic Lab Design

Dynamic analysis is strategically important, but it should not be part of the default v0.1 scan path. The v0.1 product should stay static, provenance-first, and safe to run against arbitrary repositories. Phase 5 should be planned now as a separate opt-in lab track so future execution is deliberate, auditable, and isolated.

## Recommendation

Ship v0.1 without dynamic execution. For v0.1, add only the concepts that make Phase 5 easy to attach later: policy labels for lab eligibility, evidence schemas that can hold lab observations, and UI language that makes static versus dynamic evidence clear. The first runnable lab should target v0.2+ or an explicitly experimental build.

## Threat Model

Lab mode assumes every analyzed skill, MCP server, script, dependency hook, and setup command may be malicious. Expected behaviors include reading files, enumerating environment variables, spawning subprocesses, downloading payloads, opening network connections, attempting persistence, exhausting resources, and probing container boundaries.

The lab worker itself is sensitive. It must not have production credentials, the Docker socket, host source mounts with write access, cloud metadata access, or access to the main application filesystem beyond a narrow job API.

## Non-Goals

- No dynamic execution in the default CLI or server scan.
- No Windows or macOS lab worker in the first implementation.
- No Docker socket mounted into analyzed containers.
- No host networking.
- No raw prompt, request body, or full filesystem capture by default.
- No attempt to prove perfect containment. Lab output is additional evidence, not a guarantee of safety.

## Architecture

Phase 5 should introduce a separate `skill-issue-lab` worker binary and crate. The server remains the control plane and system of record; the lab worker consumes explicit lab jobs, runs them in isolated Linux sandboxes, redacts observations, and writes structured evidence back to Postgres.

Core components:

- Control plane: server routes, policy checks, audit events, job creation, and result display.
- Lab worker: Linux-only process responsible for sandbox lifecycle and observation collection.
- Sandbox runtime: rootless Docker or Podman first; gVisor/Firecracker evaluated after the basic worker model is stable.
- Evidence model: structured process, filesystem, network, canary, and exit-status observations with redaction before persistence.
- Artifact store: disabled by default; when enabled, local content-addressed storage with TTL, size caps, and explicit admin opt-in.

## Safety Baseline

Every lab run must enforce:

- Explicit opt-in per run or per policy rule.
- Static scan and policy evaluation before execution.
- Linux-only worker host.
- Rootless runtime where possible.
- No Docker socket inside analyzed containers.
- No host source mount with write access.
- Read-only input snapshot plus isolated writable tmpfs/output directory.
- Dropped Linux capabilities and `no-new-privileges`.
- Non-root container user.
- CPU, memory, process, file-size, and wall-clock limits.
- Default-deny egress with optional allowlist profiles.
- No inherited host environment variables except lab canaries.
- Redaction before persistence.
- Audit event for job request, start, completion, failure, and artifact access.

## Execution Model

The worker should not blindly run arbitrary repository commands. It should execute only bounded harness actions selected from static analysis:

- MCP declaration probe: start a declared server with sanitized env and observe startup behavior for a short window.
- Skill dry-run harness: render/read skill files and execute only explicitly configured test commands in lab fixtures.
- Script behavior probe: run high-risk scripts only when policy allows lab execution and arguments are generated by Skill Issue.
- Dependency-install probe: future-only, disabled by default, because install hooks can be especially risky.

Each action gets a reproducible invocation record: source scan ID, asset ID, command, args, image digest, sandbox profile, timeout, egress profile, canary set, and expected observation categories.

## Observations

Initial observations should be simple and robust:

- Process starts, exits, subprocesses, and exit codes.
- Files read or written inside the sandbox workspace when observable through wrapper instrumentation or snapshot diffs.
- Network connection attempts by destination host/IP/port/protocol, with default redaction and no body capture.
- Canary file reads and canary environment variable access.
- Suspicious output snippets after redaction.
- Resource limit events such as timeout, OOM, process limit, or output cap.

Later Linux worker versions can add eBPF-based process/network/file monitoring once the basic model is proven.

## Scoring and Policy

Lab evidence should feed policy as an additional signal. It should not replace deterministic static/provenance rules.

Suggested actions:

- Canary access: block.
- Network attempt under default-deny profile: review or block based on asset intent.
- Runtime download or spawned shell: block when not declared and approved.
- Timeout/resource exhaustion: review.
- Clean lab run: evidence only, never automatic approval by itself.

## Milestones

Phase 5.0: Design and schema
- Finalize threat model, sandbox profile schema, lab job schema, and observation schema.
- Add no-execution fixtures that validate serialization and policy decisions.

Phase 5.1: Worker skeleton
- Add `skill-issue-lab` crate and binary behind a feature/profile.
- Implement job polling, sandbox profile parsing, and dry-run mode that does not execute untrusted code.

Phase 5.2: Local sandbox MVP
- Run a controlled benign fixture in rootless Docker/Podman with strict limits.
- Persist structured observations and audit events.

Phase 5.3: Canary and egress controls
- Generate lab-only canary files/env vars.
- Enforce default-deny egress and record blocked connection attempts.

Phase 5.4: High-risk asset probes
- Add MCP declaration startup probes and script behavior probes gated by policy.
- Compare observed behavior against static intent and historical baseline.

Phase 5.5: Hardening evaluation
- Evaluate gVisor/Firecracker, eBPF observation, artifact TTL cleanup, and worker isolation tests.

## v0.1 Boundary

For v0.1, Skill Issue should not execute repository code. Acceptable v0.1 work is limited to documenting Phase 5, reserving schema concepts, and making UI/API language distinguish static/provenance evidence from future dynamic lab evidence.
